# 历史客户项目补录与销售漏斗

历史资料先形成可审阅清单，经用户接受后由当前公司管理员通过受约束的应用接口导入。原件、原始沟通、真实金额与回执只存本机公司数据库及私有目录；公开仓库只含通用代码和合成测试。

## 查看漏斗

进入“销售预测与回款分析 → 销售预测”，使用现有日期和人员范围。销售漏斗表在预测页优先展示，按当前线索、开放商机阶段、成交/履约及掉单汇总；点击阶段或数量展开明细，可搜索并打开客户、商机、线索和有权查看的合同。管理员同样默认本人，全公司/其他人员仍受数据权限控制。没有新增独立业务页面。

历史补录按已核实的资料来源日期归期；日常新建按创建日期归期。来源日期待核实的记录在显式勾选的待核池中显示；这些日期不是实际成交或掉单日期。预测模块继续以预计成交日期及实际关闭日期归期，不用补录时间制造历史业绩。

具名且已核报价的渠道掉单与主体待核候选分开显示金额；后者不计入具名总价。未知总价保留待确认，月费/单位报价不与固定总价混加。掉单报价是未成交商业机会，不能作为实际收入损失或应收债权。

## 管理员导入接口

能力契约见 `GET /sales-intake/schema`。所有身份及公司来自认证上下文；不接收自报 tenant/actor。

1. `POST /sales-intake/archives`：逐份保存不超过1MiB的真实原件，按SHA256复用。同一公司总计最多100份。较大文件保留私有原件位置及摘要，不能声称已上传其全部二进制。
2. `POST /sales-intake/preview`：严格清单、现有客户/合同版本、负责人有效性、客户去重及来源引用预检。返回摘要、指纹及30分钟有效预览。每批至多200客户/200事项/500跟进/500行动，不能任意执行数据库语句。
3. `POST /sales-intake/commit`：原管理员、预览编号和指纹一致才提交；再次校验来源版本，Serializable事务写入正式对象、来源映射、命令回执及审计。相同请求或批次重放不重复建档；已导入批次内容变化拒绝覆盖。
4. `GET /analytics/funnel`：读取当前正式线索/商机，叠加日期、人员及逐对象可见范围，超过10000条拒绝截断统计。`GET /sales-intake`保留同一读取服务的兼容入口。

客户PPT归线索，报价归商机，同一事项报价修订归内部跟进；实际客户沟通单独标记。已转换线索不再重复计入漏斗。历史未知金额在存储层以金额存在标记区分，占位零不作为已知零价对外显示；工作台、明细和预测统一投影。正式产品报价后可更新已知价格及总额口径。

合同草稿只保留已证实的主体、金额、明细和付款文字；日期未知不造付款节点，不生成正式债权、发票、收款或签章事实。已有有效合同只建立商机关联，不改变原合同客户、金额、负责人或财务记录。催收行动沿用仍有效的原合同负责人；历史负责人尚未归部门时保留其原归属，不虚构组织、不转移债权责任。新分配仍要求部门有效。开票未收是合同应收的另一视角，不能相加。导入不触发历史通知、群消息、审批或外部同步发送。

## 验证

本批 `pnpm check`：405项API测试、40项Node检查及类型/lint/build通过。`scripts/sales-intake-smoke.mjs`必须显式启用写入且数据库名匹配 `tb_crm_test_*`，隔离真实MySQL通过54项HTTP/数据核对：身份越权、跨公司及源版本冲突、SHA原件复用、预览指纹、原子回滚、多方式重放、草稿无债权、旧合同不改写、负责人、报价版本、未知金额投影、期限口径、本人默认和漏斗钻取服务。该合成MySQL回归已加入GitHub CI独立数据库作业。测试数据全部合成，不代表整套商用验收。

## 补齐已有事项的行动与预计日期

`POST /sales-intake/activities`（`sales.intake.activities@1.0`）仅当前公司管理员人工会话可用，不开放智能体写入。一次1—100个已有审阅事项；每条带事项及行动的当前版本、来源事项键、预计成交日及是否估算、日期依据、下一步及拟定日期。沿用同客户未完成行动，缺日期才补，不复制既有行动。可追加一条明确标识“历史资料整理”的跟进，来源必须属于原事项；这不代表发生新联系。

事务内重建该事项的跟进次数/最近来源日期并关联下一步，保留未知实际签约/关闭日。估算存在结构元数据和备注中；看板标注“日期估算”。历史跟进的导入创建时间不会冒充实际联系日期。幂等回放不新增，版本冲突整批回滚，禁止财务、审批、消息、钉钉外发等副作用。

`sales.contract.plan@1.0` / `POST /sales-intake/contract-plans` 为已签合同补充成交路径行动表单：批量上限100、当前合同版本校验、合同实际负责人、合同/分期/开票/收款引用、事实与拟定路径分栏、同合同表单去重及命令审计。只创建待办，不修改原合同、财务、审批或外发。合同详情和客户详情可按模块及人员范围读取关联表单。未知验收/付款日期仍需实际核对；拟定工作日期不冒充客户承诺。

`sales.action.calendar@1.0` / `POST /sales-intake/action-calendar`把有效行动转为本地拟定推进时段，取实际执行人、校验版本和忙闲，稳定引用行动及客户。新时段必须在今后且不晚于2060年，按行动去重；原始钉钉日程不改写。不发送消息，不改变财务日期。已签事项的成交归期仅可沿用关联有效合同的已知签署日期，元数据记录`eventTimeKnown=false`，不推定具体事件时刻；没有依据的实际关闭日继续为空。

## 从看板进入商机并记录跟进

卡片同时显示商机、客户、负责人、预计成交日、跟进次数/最近日期和下一步；商机详情及跟进可直接进入，客户链接仍检查客户模块权限。商机详情的跟进页按来源日期显示内容/结果和下一步，估算单列标识。

`opportunities.follow@1.0`为人工业务命令：当前对象版本、商机修改、跟进创建及客户可见权限；严格内容/方式/下一步/日期参数。记录直接关联商机和客户，原子更新最近跟进和次数。可明确勾选同时为当前商机实际负责人生成行动与拟定本地日程，另检查行动创建权、负责人启用及该日空闲时段。冲突整笔回滚，重复请求复用回执，不影响合同/财务/审批，不向外部发送。客户、报价和后续跟进继续使用原对象权限。
