### 高：H1．私有任务附件元数据经项目历史越权暴露，且可进入 MCP（#13）

**位置**

- `apps/api/src/modules/workspace/workspace.service.ts:1116`：新增任务附件快照。
- 同文件 `:500`：项目详情返回全部项目交付事件。
- `apps/api/src/modules/capability/mcp.controller.ts:112`：`workspace.get`直接返回上述详情。

**问题与证据**

任务完成事件保存附件 `id/filename/sha256/size`。项目详情查询事件只过滤企业和项目，没有按照任务可见范围过滤；相比之下，紧接着查询 `related.tasks` 时使用了任务权限过滤。

附件服务直接读取任务附件时会检查任务范围，但事件投影绕过了这层限制。新增快照把附件元数据带入了已有的宽范围事件读取路径。

**失败场景**

跨部门员工 A 仅被分配项目中的任务 A，因此取得项目协作读取权限。任务 B 属于另一员工，A 无权读取任务 B 或其附件列表。B 完成后，A 仍可通过项目详情或 MCP `workspace.get`取得 B 附件的文件名、摘要、大小和编号。

文件名本身可能包含客户名称、合同编号等敏感信息。**这是元数据泄露；未发现此路径返回二进制正文。**

**建议修改**

项目事件投影必须按事件所属任务的当前权限过滤，或对不可见任务的附件证据做脱敏。HTTP 与 MCP 共用该投影。增加“两名跨部门任务执行人”的反例，断言禁止直接读取的附件元数据也不能从项目历史取得。

### 中：M1．关闭后重开不复核原处理人资格，绕过活动工单人员约束（#12）

**位置**

- `apps/api/src/modules/workspace/service-ticket-policy.ts:25`
- `apps/api/src/modules/workspace/service-ticket.service.ts:235`
- `apps/api/src/modules/system/users/user.service.ts:257`

**问题与证据**

人员变更检查排除了 `closed/cancelled` 工单，这本身合理；但重开直接进入 `assigned`，保留旧 `assigneeId`。只有 `assign` 操作调用 `deliveryPeople` 校验有效账号、部门、角色和权限，`reopen` 没有相同检查。

**失败场景**

工单关闭后，原处理人停用、转为老板角色，或调到另一部门。管理人随后重开工单，系统重新生成一条分配给不合格人员的活动工单：

- 停用或失去执行权限者无法处理；
- 调部门后仍有执行权限者，会自动恢复该工单职责，绕过新的指派资格检查。

之后可以人工转派恢复，因此不是不可恢复的数据损坏，但破坏了人员交接约束。

**建议修改**

重开时在同一事务中重新验证接收人；不合格时要求选择有效接收人，或退回未指派状态。补充“关闭→停用/调部门/撤权→重开”及与人员变更并发的测试。

### 中：M2．附件只更新父版本，没有校验调用方预期父版本（#13）

**位置**

- `apps/api/src/modules/workspace/attachment.service.ts:107`
- 同文件 `:126`、`:201`、`:211`
- `apps/api/src/modules/workspace/attachment-contract.ts:24`

**问题与证据**

上传白名单和契约不包含父记录版本。撤回只校验附件自己的 `updatedAt`。两者都会重新检查当前父对象状态并更新父版本，但不会判断用户看到的父记录是否已经过期。

因此目前成立的是“附件变化阻止旧页面完成/验收”，不是双向完整的父版本检查。

**失败场景**

用户在某轮处理中打开上传页面；另一人随后提交方案、退回重办。延迟上传抵达时父对象已经再次可编辑，请求会成功，把上一轮准备的材料加入新一轮证据。Serializable 只能保证执行顺序，不能识别过期用户意图。

**建议修改**

上传及撤回增加 `expectedParentUpdatedAt`，在事务中校验；任务附件明确校验任务版本及相关项目审核状态。补充“可编辑→冻结→重办→旧请求抵达”的反例，同时保留成功请求的幂等重放语义。

### 中：M3．企业附件配额与整库备份预算未衔接（#13）

**位置**

- `apps/api/src/modules/workspace/attachment.service.ts:127`
- `deploy/data.mjs:29`、`:41`
- `deploy/backup-format.mjs:4`

**问题与证据**

附件仅限制每企业原始字节数为 16 MiB；备份却使用整库 `mysqldump --hex-blob`，并把输出缓存在内存，限制为 128 MiB。十六进制表示使附件正文约膨胀为两倍，压缩发生在导出之后，不能避免导出阶段超限。

**失败场景**

- 四个企业各保留 16 MiB 附件，仅附件十六进制正文就约 128 MiB，加上其他 SQL 必然超限。
- 单企业已有较大业务库时，新增约 32 MiB 的附件 SQL 也可能使备份失败。

这不是“16 MiB 必然无法备份”，而是**上传成功并不保证仍处于可备份容量内**。现有 smoke 验证了合成库恢复，没有覆盖接近整库上限的场景。

**建议修改**

试点前明确单库租户数量与备份容量预算，增加容量预警和接近上限的备份恢复测试；需要扩容时改用有明确资源边界的流式导出/加密。性能方面还需验证并发上传的租户范围聚合锁竞争，以及备份期间的内存峰值。

### 低：L1．下载缺少显式 `nosniff`，但不能据此认定已存在存储型 XSS（#13）

**位置**

- `apps/api/src/modules/workspace/attachment.controller.ts:20`
- `apps/api/src/main.ts:8`
- `apps/web/src/pages/workspace/AttachmentPanel.tsx:85`

**问题与证据**

下载路由显式设置了 `Cache-Control: no-store`，未设置 `X-Content-Type-Options: nosniff`；未找到全局补充设置。当前实际响应是 JSON/Base64，前端使用 `application/octet-stream` Blob 和 `download` 属性保存文件。

因此，缺少服务器 `Content-Disposition` **不等于当前接口会内嵌执行 PDF/图片**；它并非原始文件流接口。

**失败场景**

当前实现依赖 JSON 响应类型及浏览器保存路径。以后增加直接下载或预览时，如果沿用现有头部策略，会缺少明确的内容嗅探防护。

**建议修改**

显式添加 `nosniff`，增加响应头断言，并在契约中明确 JSON 下载协议。若改成二进制响应，再同时设置受控 `Content-Type` 和安全编码的 `Content-Disposition: attachment`。
