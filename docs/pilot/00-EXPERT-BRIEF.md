# 伴圆 CRM 从“工程候选”到“真实可用” · 专家视角简报与重写后的题目

日期：2026-11-01 · 版本：v2（已按 [Codex 审计](02-CODEX-AUDIT.md) 修订） · 基线：`feat/agent-delegated-execution`（619eb2b，PR #11 head）；栈顶已至 PR #13 `feat/private-evidence-attachments`（b09b7ca），#1–#13 堆叠，均未合并 · 状态：设计输入，待产品负责人确认 · 配套：[详细方案](01-PRODUCT-TECH-DESIGN.md)

## 0. 结论先行

1. **工程底座可以复用，但还没有可审计的真实试点证据。** 当前分支已有正式安装与加密备份恢复、账号会话、客户导入去重、销售交接、报价版本、合同变更、交付验收、应收台账、审批转审、智能体受控执行，以及 PR #12 售后工单（独立复核关闭）与 PR #13 私有附件证据，并有约 1,500 项真实 MySQL 检查（不含 #12/#13 各自新增的 111 与 99 项）。但证据都来自合成数据和构建者自测；测试数量不能证明真实业务正确——审计发现新签合同仍生成“演示：签约后 30 天全额回款”计划、输单不写关闭日期、已输单商机签约会被直接改为赢单、系统任务没有执行主体。
2. **最大的风险已经从“功能缺失”变成“交付形态”**：13 个 PR 层层堆叠、全部待验收；C1–C9 九条线同时推进，交付/财务/智能体做得很深，而销售每天打开 CRM 的理由（今日待办、提醒、续费、手机录入、周会视图）还很薄。
3. **专家会做的第一件事是“收口”**：冻结新领域扩展 → 盘点 PR 依赖并对具体 SHA 验收出 v0.3 候选 → 先补业务正确性（付款计划、期初余额、阶段终结、系统命令、财务角色、MFA）→ 再补日常使用与迁移 → 用 1 个真实销售团队做**有限范围**试点 4 周。试点、工程合并、商用验收是三道独立的门。
4. **“初步用起来”的判定**：一个 ≥5 人的真实销售团队连续 4 周把 CRM 作为唯一的客户与商机记录工具；周会只用 CRM 的漏斗视图；月底合同额与回款额与财务台账逐笔对平；试点期未发生数据丢失事件。
5. **业务形态判断（需确认）**：数据模型中的 `yonyouCode/yonyouProduct/serviceExpiry` 与合同类型（软件销售、实施、维保、外包、AI FDE、SaaS 订阅、渠道）显示使用方是**用友生态的渠道/实施服务商**，续费维保是现金流核心，但系统中尚无续费流程。

## 1. 顶尖专家会怎么设计

参照：Salesforce Sales Cloud、HubSpot、Pipedrive、Attio；国内纷享销客、销售易。

| 原则 | 含义 | 本项目现状 → 应做 |
| --- | --- | --- |
| 先让销售每天打开 | CRM 的价值来自持续录入；录入来自“对我有用” | 缺今日待办推送、手机端 → 补齐 |
| 阶段由买方行为定义，赢单在签约 | 交付不属于商机漏斗 | 种子 9 阶段含交付/验收/结项 → 重定义为 5+赢/输 |
| 续费是独立流水线 | 到期前 90 天自动生成续费商机 | `serviceExpiry` 只被 AI 摘要读取 → 新建 |
| 主数据先干净 | 重复客户是 CRM 失败第一原因 | 已有规范化名称查重 → 补信用代码唯一与合并 |
| 迁移是上线的一半 | 存量客户、联系人、商机、合同、应收期初都要进来 | 仅能导入客户 7 列 → 扩展 |
| 管理节奏内建 | 周会、预测、停滞商机 | 有看板、无周会视图与预测快照 → 补齐 |
| 财务口径以财务为准 | CRM 不记账但要能对账 | 应收台账已有独立复核 → 直接复用，补对账导出 |
| 小步发布、真实反馈 | 每 1–2 周一个可安装版本给真实用户 | 13 个堆叠 PR 未合并 → 发布列车 |
| 先上线再做智能 | AI 依赖干净数据和真实用法 | 智能体委托已很深 → 试点期冻结扩展 |

## 2. 专家会做、但你没要求的事

1. **合并发布策略**：先画 PR 依赖图（#11 基于 #9，并非单链）、列迁移链，再由负责人对最终候选 SHA 验收出 `v0.3.0-rc`；之后每个功能一个短 PR，直接以 main 为基线。
2. **试点范围例外矩阵**：逐项写明试点开放、隐藏、禁止用于真实业务的能力（如复杂审批、开票退款延期；售后与附件纳入试点），由负责人签字；它们仍是商用门槛，不因试点被取消。
3. **数据审计先于迁移**：用存量 Excel 算重复率、缺失率、无主客户、停滞商机，迁移前后出对账单签字。
4. **锁定指标口径**：新签、回款、应收、赢单率、销售周期、续费率、预测准确度、停滞商机。
5. **采用度度量**：周活跃、每人跟进数、商机 14 天更新率——用于发现阻力，不用于考核个人。
6. **输单原因与竞品**：输单必填，季度复盘。
7. **一页纸“今天能用什么”**：PROGRESS 面向工程，用户需要的是能力清单和限制，不是检查项数。
8. **运维兜底**：定时备份（当前需手动）、HTTPS 反向代理模板、监控告警、恢复演练日历。
9. **账号安全与职责分离**：老板、管理员、财务强制 MFA；新增最小权限的财务角色（当前只有管理员能登记和复核收款），或至少配置 2 名管理员。
10. **退出保障**：版本化的业务全量导出（不含密钥），并实测能在空库重建关键关系；配套切换与回退 runbook。
11. **个人信息保护**：采集真实素材前先交付数据处理说明（目的、最小字段、留存期限、受托处理、权利响应、事件处置），而不只是脱敏。
12. **培训与支持**：45 分钟培训、操作卡、首周每日答疑、问题看板与响应时限。
13. **试点退出条件**：第 2 周销售有效周活跃 <50% 即暂停复盘，不继续加功能。
14. **期初余额单独建模**：期初应收是截止日余额，不能伪装成一笔“已复核收款”，需双人在系统内确认，且不计入当期回款。
15. **系统执行主体**：续费生成、预测锁定等定时任务需要服务端建立的受限系统主体，不能借用管理员会话。

## 5. 除了你和我，还有什么能证明结果正确

1. **财务台账**：CRM 的合同额、已确认回款与财务账逐笔对平；每笔差异有金额、类别、责任人和签字。
2. **用友伙伴门户到期清单**：与 CRM 续费商机一一对应。
3. **迁移对账单**：迁移前 Excel 与迁移后 CRM 的数量、金额一致，主管与财务签字；客户重复率由人工裁定抽样计算，不用系统自己的查重算法自证。
4. **真实用户行为日志**：试点期活跃、跟进、商机更新数据。审计日志由系统生成，不自动独立，须冻结原始日志后由业务方按指标字典独立重算。
5. **可用性测试**：5 名真实销售无人协助完成每个关键任务（按任务分别计）的成功率、耗时与 SUS 分数。
6. **业务负责人签收**：主管、老板、财务按验收清单逐项签字。
7. **CI 记录**：GitHub Actions 的实际运行链接（已有体系，继续保留）。
8. **第三方安全扫描/渗透报告**。
9. **恢复演练记录**：按日历在目标服务器上执行并留存回执。
10. **独立审计**：Codex（gpt-6-astra）对方案与代码的审计，问题逐条关闭。
11. **钉钉/飞书真实企业联调记录**。

> 现有约 1,500 项 MySQL 检查是很强的工程证据，但它们都由构建方编写和运行。上面 1–3、5、6、8 是“构建方之外”的证据；4 和 9 需由非构建方复验才算独立。每项证据须绑定同一版本 SHA，并在证据索引中写明独立复验人。

## 6. 重写后的题目

> **任务：把 os-crm（伴圆 CRM / PartnerOS）从“工程候选”收口为一个真实 B2B 销售团队可以日常使用的 v0.3 试点版，并用试点证据证明它被用起来了。**
>
> **现状**：`osborn-studio/os-crm` 在 `feat/agent-delegated-execution` 分支上已有正式安装与加密备份恢复、账号会话、客户导入去重、销售交接、报价版本、合同变更、交付验收、应收台账、审批转审、智能体受控执行、售后工单与私有附件证据，PR #1–#13 堆叠未合并；所有验证均基于合成数据，尚无真实用户。使用方为用友生态的渠道/实施服务商（待确认）。
>
> **目标与成功标准**（试点 4 周，≥5 名销售 + 主管 + 老板 + 财务）：
> 0. 试点范围：销售—合同—回款主线，加上已验收项目的售后工单与交付/售后附件证据（PR #12、#13）。
> 1. 存量客户、联系人、未关闭商机、合同（含付款计划）与期初余额完成迁移，迁移对账单由主管与财务签字；客户重复率 <2%（人工裁定抽样）；
> 2. 销售有效周活跃 ≥90%，人均每周 ≥5 条跟进，活跃商机 14 天更新率 ≥80%（按 METRICS.md 口径，排除导入/系统/智能体来源；原始日志由业务方独立重算）；
> 3. 周会只用 CRM 的漏斗/预测视图；月底新签与已确认回款与财务台账逐笔对平，关键未解释差异为 0；
> 4. 到期 90 天内的服务权益期全部有且只有一个续费商机，与用友伙伴门户到期清单一致；
> 5. 目标服务器 HTTPS 入口实测通过、每日自动加密备份并异机复制、试点期至少 1 次恢复演练通过（RPO ≤24h、RTO ≤4h）、工作时间可用性 ≥99.5%、试点期未发生数据丢失事件；
> 6. 5 名销售可用性测试中每个关键任务 ≥4/5 无协助完成，SUS ≥70；
> 7. 试点期内试点客户的售后问题全部以工单在 CRM 处理，关闭均经另一项目管理人复核，所附证据可按权限下载并通过 SHA256 校验。
>
> **工作顺序**：
> 1. **收口（G1）**：画 PR 依赖图与迁移链，负责人对最终候选 SHA 验收，形成 `v0.3.0-rc` 安装包；试点期冻结财务扩展、审批高级能力、智能体扩展与售后/附件的后续扩展（SLA 自动升级、外发、客户门户、病毒扫描、对象存储），只修缺陷。
> 2. **发现**：先交付试点数据处理说明，再用原始素材（销售 Excel/名片、伙伴门户导出、合同与回款台账、周会材料、输单复盘、跟访、7 类角色访谈）产出数据审计报告、指标字典、付款条款样本、阶段迁移矩阵，冻结 v0.3 范围与例外矩阵。
> 3. **先补业务正确性**：合同付款计划（替换演示规则）；期初余额双人确认；商机终结语义与停用阶段过滤；受信系统命令；财务角色；MFA。
> 4. **再补日常使用**：暂存—分块发布的可恢复迁移；信用代码唯一与收窄的客户合并；阶段重定义；续费权益与周期；今日待办与外发箱（至少一次投递）+ 钉钉/飞书单向工作通知；移动端 4 页；周会视图与预测；业务导出。
> 5. **上线兜底（G2）**：HTTPS 入口实测、宿主机定时加密备份与异机复制、监控告警、恢复演练、切换/回退 runbook、事故分级、培训与支持；负责人、老板、财务签字例外矩阵。
> 6. **试点**：4 周真实使用，每周对账与复盘，按第 2 周采用度决定继续或暂停。商用验收（G3）仍按 COMMERCIAL_ACCEPTANCE 另行进行。
>
> **约束**：遵守 AGENTS.md 与 COMMERCIAL_PLAN 的发布门槛；新写入走能力契约，人工写入用 `runCommand`、系统写入用受限的系统命令；不伪造凭据、复核或审批事件；不提交真实客户数据；智能体保持当前边界；不得把未运行的检查写成通过。
>
> **证据**：除 CI 与真实 MySQL 检查外，必须产生构建方之外的证据：财务对账、伙伴门户对照、迁移对账单（人工抽样查重）、业务方独立重算的采用度、可用性测试、业务签收、第三方扫描、恢复演练回执；全部绑定同一 SHA 并列入证据索引。Codex gpt-6-astra 审计问题逐条在实现 PR 中以测试关闭。
>
> **待确认**：业务形态与产品线；典型付款条款；试点团队；存量数据位置与规模；期初余额口径与财务确认人；财务角色还是双管理员；例外矩阵；钉钉还是飞书；部署服务器与异机备份；续费规则；PR 的验收方式与时间。
