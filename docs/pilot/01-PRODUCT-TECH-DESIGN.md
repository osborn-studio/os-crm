### 1.3 判断

已有工程底座（事务、幂等、权限重载、真实 MySQL 检查）可以复用，但**不能用测试数量推断真实业务正确性**：财务期初、合同付款计划、阶段状态、迁移原子性、系统任务身份和运维责任都需要在真实数据之前补上契约与反例测试。v0.3 不开新领域，只做：收口发布 + 迁移 + 合同付款计划 + 日常使用 + 上线兜底 + 试点运营。

## 2. 试点定义

### 2.1 对象与规则

- **对象**：1 个销售团队（≥5 名销售 + 1 名主管）、老板、1 名财务、**2 名管理员**（或交付独立财务角色，见 §4.10），以及负责试点客户的 ≥2 名项目管理人（售后关闭需另一人复核）与实施人员。
- **时长**：准备约 5–7 周（§11）+ 正式使用 4 周。
- **规则**：老板书面宣布试点期 CRM 为唯一客户与商机记录工具；周会只用 CRM 视图。
- **成功标准**：见简报第 6 节。
- **退出条件**：第 2 周销售有效周活跃 <50% → 暂停、复盘、修正后再开始；不以加功能应对。

## 4. 业务设计（仅 v0.3 增量）

### 4.0 执行主体：人工命令与受信系统命令

现有 `runCommand` 每次重读人工会话、用户、角色与权限（`command-runner.ts:58–104`），系统任务无法也不应借用管理员会话。

- 新增 `runSystemCommand`：与 `runCommand` 共用事务、Serializable 重试、requestKey 幂等与业务校验；执行主体由服务端为**单个租户 + 单个任务名**建立，携带 `jobName`、`policyVersion`、`jobRunId`；只能调用该任务白名单中的能力（如 `renewal.generate`、`forecast.lock`、`todo.digest`）。
- 审计中 actor 显示为 `system:<jobName>`，不冒充任何用户；任何外部输入（HTTP、MCP 工具 body）都不能声明 `tenantId/actorId/system`。
- 智能体执行仍沿用人工委托主体，但审计必须带操作来源（`human / agent / system / import`），供 §5 指标排除。
- 此契约完成并有反例测试后才实施 Worker（§4.7）。

### 4.1 迁移导入：暂存 → 分块发布（部分提交、可恢复）

选择“暂存后分块发布”，并明确语义为**部分提交、可恢复**，不宣称整批原子。

1. **迁移窗口**：管理员申请、老板批准，限时（默认 72 小时）、绑定租户与已批准批次清单、可随时撤销；每块发布前重检窗口、操作者权限与会话。窗口关闭后未发布块停止，保持 `paused` 可在新窗口续传。
2. **暂存**：上传后所有行写入 `ImportStagingRow(batchId, resource, sourceRowKey, payloadHash, status, errors)`，`(batchId, resource, sourceRowKey)` 唯一。预检**不创建业务记录，但保存预检证据**（与现有导入一致）。
3. **负责人映射**：预检输出源负责人文本 → 系统用户的映射表，需主管确认；停用、跨部门、非销售账号拒绝；保留原负责人文本。
4. **分块发布**：每块 ≤500 行，单独一个 `runCommand` 事务，在**同一事务**内写业务记录、更新暂存行状态、写块回执；块键 `(batchId, chunkNo)` 唯一。不在一个可重试回调里开多个独立事务。重放已发布块直接返回原回执。
5. **跨批防重**：业务记录保存 `sourceSystem + sourceId`，`(tenantId, resource, sourceSystem, sourceId)` 唯一，换批次、换 requestKey 也不能重复导入同一源行。
6. **批次状态机**：`staged → previewed → publishing ⇄ paused → published | cancelled`。取消只停止未发布块；已发布记录按正常业务删除/更正流程处理，不自动回滚。
7. **时间字段**：分别保存 `sourceCreatedAt`（源业务时间）、`importedAt`、`importedBy`、`batchId`；不覆写 `createdAt`。
8. **已签历史合同**：以迁移证据（批次 + 源合同号 + 签约日）标记已签，不伪造 `ApprovalEvent`。
9. **迁移对账单**：每类资源输出“源行数 / 发布 / 跳过重复 / 错误 / 金额合计”，与源 Excel 合计比对。

### 4.2 期初应收：独立的“期初余额确认”

期初应收是截止日的时点余额，不是当期到账，**不建模为收款登记，不伪造凭据与复核事件**。

- 新表 `OpeningBalance(tenantId, contractId, cutoffDate, contractAmount, receivedToDate, outstanding, allocations[], sourceDigest, status, preparedBy, confirmedBy, confirmedAt)`；`allocations` 把截至截止日的已收分配到各付款计划。
- 由管理员按迁移批次准备；由**另一名授权用户（财务）在系统内登录确认**，确认人取自认证上下文。
- 确认后：付款计划的 `outstandingAmount` 按分配扣减；该金额**不计入任何期间的“已确认回款”**；`finance-policy` 的勾稽规则扩展为“期初已收 + 有效核销 = 计划已收”。
- 截止日之后的真实回款照常走收款登记/复核/核销；若补录截止日前的凭据，必须先作废对应期初分配，防止重复计算。
- 更正：确认后的期初余额只能通过“期初更正”事件修改，留双人记录。

### 4.3 客户主数据补强

- `creditCode`：可空 + `@@unique([tenantId, creditCode])`（MySQL 唯一索引允许多个 NULL，无需生成列）；空白归 NULL；去空格、大写、18 位校验码校验；创建、修改、导入共用同一校验函数。建约束前先出冲突报告并人工处理。
- **客户合并（v0.3 收窄）**：只允许合并“被合并方无商机/报价/合同/订单/项目/收款/审批/续费权益/智能体建议”的重复客户；联系人、跟进、行动可迁移。预检逐表列出迁移项，并显示合并后**谁新增可见性**。历史快照与事件 evidence 不改写；被合并方标记 `merged`、保留 `mergedIntoId` 与别名映射，名称指纹与信用代码释放给保留方。有业务关联的重复客户进入人工清单，v0.3 不处理。
- 不提供撤销；因范围限定为无业务关联记录，误合并可通过拆分联系人人工恢复。

### 4.4 合同付款计划（替换演示规则）

- 合同审批前必须录入付款计划（期数、金额、到期日或触发条件）；合计必须等于合同含税金额；签约时按录入计划生成 `PaymentPlan`，删除“签约后 30 天全额”演示逻辑。
- 合同变更守卫沿用 `contract-change-policy`：已有核销的计划不可改金额；未执行计划可调整，留变更记录。
- 迁移的已签合同按源台账导入计划（§4.1），期初部分按 §4.2。

### 4.5 商机阶段与终结语义

新阶段：

| 阶段 | 概率 | 进入条件（推进时校验已存在的事实） | 退出到下一阶段需满足 |
| --- | --- | --- | --- |
| 1 线索确认 | 10% | 已关联客户 | 需求摘要、预计金额 >0、预计成交日期、≥1 名联系人 |
| 2 需求确认 | 20% | 同上一列 | 本商机在本阶段内（`stageEnteredAt` 之后）≥1 条跟进 |
| 3 方案/演示 | 40% | 同上一列 | 存在报价版本 |
| 4 报价 | 60% | 同上一列 | 存在关联当前报价版本的草稿合同 |
| 5 商务谈判 | 80% | 同上一列 | 合同签约（只能由签约触发） |
| 赢单 | 100% | 仅合同签约 | — |
| 输单 | 0% | 原因类别必选 + 竞品 + 说明 | — |

规则写为“退出条件”，避免“进入后才能满足”的循环；条件以固定规则集存于 `OpportunityStage.exitRules`（JSON，服务端解释，不执行任意表达式），附 `rulesVersion`。

终结语义：

- 新增 `Opportunity.closedAt`、`lossCategory`、`competitor`、`type (new/upsell/renewal)`。
- 输单：`status=lost`、`closedAt=now`、`weightedAmount=0`、写阶段历史。
- 签约：只对 `status=open` 的商机置赢单；已输单商机需先由主管“重新打开”（记录原因）才能关联签约；一个商机只能关联一份赢单合同。赢单时写 `closedAt/winDate`、概率 100%、阶段历史。
- `advance`、创建、看板、`overview` 全部过滤 `isActive=true` 阶段（`isActive` 已在 `schema.prisma:599`）。

| --- | --- | --- |
| 任意阶段，`status=won` 且有已签合同 | — | 赢单，保留 `winDate`，`closedAt=winDate` |
| 任意阶段，`status=lost` | — | 输单，`lossCategory=其他`，`closedAt=updatedAt`（标注推断） |
| `status=open`，旧阶段 lead/intention | — | 1 线索确认 |
| `status=open`，旧 qualification | 满足 1→2 条件 | 2 需求确认，否则 1 |
| `status=open`，旧 proposal | 有报价 | 4 报价，否则 3 方案/演示 |
| `status=open`，旧 signing | 有草稿合同 | 5 商务谈判，否则按事实降级 |
| `status=open`，旧 delivery/acceptance/closed | 有已签合同 | 赢单 |
| 同上 | 无已签合同 | **待核对**（不落入任何阶段的漏斗统计），由主管逐条处理 |

实际旧 code 清单在 P0 用 `initialize-production.mjs` 与目标库导出逐一核对，矩阵必须覆盖每个出现的 code。旧阶段置 `isActive=false` 保留。停滞：当前阶段停留超过阈值（默认 30 天）进入停滞清单。

### 4.6 续费流水线

- `ServiceEntitlement`：稳定 ID（服务/授权实例），`customerId`、`productKey`、`moduleKey`、可选 `licenseRef`（伙伴门户授权号）、`status`。
- `EntitlementPeriod(entitlementId, periodNo, startDate, endDate, amount, sourceType, sourceRef, prevPeriodId)`：`(entitlementId, periodNo)` 唯一，`(tenantId, sourceType, sourceRef)` 唯一。修改到期日是更正同一期，不产生新期。
- **唯一生成路径**：维保/订阅合同签约时，由签约处理在同一事务内为合同行创建或延续权益并新增一期；续费商机赢单签约走同一路径。不另设“续费赢单生成下一期”的第二入口。
- 续费商机：`renewal.generate`（系统命令）在到期前 90 天为 `(entitlementId, periodNo)` 生成一个续费商机，`Opportunity.renewalPeriodId` 唯一；同一权益上一期续费商机未关闭时不生成下一期（防短周期连发）；负责人 = 客户负责人，公海或负责人停用时归主管并进入待分配。
- 漏跑补偿：任务按“到期日 ≤ today+90 且未生成”扫描，不依赖“恰好第 90 天”。
- 60/30/7 天提醒；到期未赢单标“流失风险”；提前续费、延期续费、部分续费（金额小于上期）、终止（权益 `status=terminated`）分别记录。
- 续费率按到期 cohort 计算（§5）。

### 4.7 今日待办与外部提醒

- **待办聚合**：行动计划到期、跟进下一步、停滞商机、续费节点、回款计划到期、待我审批。**每类调用其所属服务的权限与字段投影后再聚合**，不统一套 `customerVisibility`（联系人、财务、审批的可见范围各不相同，见 `workspace.service.ts:318–345`、`finance-policy.ts:31–58`）。在现有待办摘要（`workspace.service.ts:1207`）上扩展。
- **事务外发箱**：`OutboxEvent(id, tenantId, type, recipientUserId, payload, dedupeKey unique, status, attempts, nextAttemptAt, claimToken, leaseUntil, lastError)`，与业务写入同事务。
  - 领取：短事务 `SELECT … FOR UPDATE SKIP LOCKED` 选行并写 `claimToken + leaseUntil` 后提交；**事务外**调用钉钉/飞书；按 `claimToken` 条件更新结果。租约过期可被重新领取。
  - 语义：**至少一次**投递，不宣称恰好一次；P0 验证所选平台是否支持请求级幂等，不支持则接受极少重复并在消息中带业务链接。
  - 指数退避，8 次后死信；管理员可查看、重放。
  - 投递前重检收件人当前状态与权限（交接、停用后不发）；消息只含最小提醒与鉴权链接，不含客户详情、联系人或金额原文。
- 渠道：钉钉或飞书工作通知（单向，企业二选一，需企业凭证与联调回执）+ 站内。
- 频率：每人每天 09:00（租户时区）一条待办摘要 + 审批即时通知；可关闭摘要。
- **任务调度锁**与消息领取锁分开：调度用 `JobRun` 租约行（`jobName` 唯一，带递增 `fencingToken`，写入时校验）；不使用 `GET_LOCK`（连接级锁，断连即失效）。

### 4.8 移动端最小可用

响应式 4 页：今日待办、客户搜索与详情（含联系人、商机、最近跟进）、写跟进（含下一步与提醒时间）、审批（查看快照并同意/驳回）。窄屏下主布局改为顶栏 + 抽屉菜单；其余页面显示“请在电脑上操作”。看板不进入移动范围。在钉钉/飞书工作台以 H5 打开，账号密码登录（免登属 C8）。用 375px 宽实机与 Playwright 移动视口验证。

### 4.9 周会视图与预测

- 周会视图：本周新增/推进/赢/输、停滞清单、按负责人漏斗、本月预计成交；数据库聚合，不在应用层加载全量对象。
- 预测：
  - `ForecastSubmission`：销售每周一至周三可多次提交本人本月/本季“承诺/最好/漏斗”，每次一个版本（只追加）。
  - `ForecastLock`：周三 18:00（租户时区）由系统命令锁定，记录每人当周最后一个版本 ID 与当时团队成员；某人未提交则锁定记录标 `missing`。
  - 主口径 = 销售锁定版本汇总；主管可提交“团队调整”作为单独一行，不替代汇总。
  - 期间：月 `YYYY-MM`、季 `YYYY-Qn`；跨月周按锁定日所在月归属。
- 采用度（仅主管/老板）：见 §5 定义。

### 4.10 导出、对账与财务角色

- **列表导出**：当前权限范围与筛选，CSV；手机号/邮箱按权限脱敏；以 `=+-@` 开头的单元格加前缀防公式注入；写审计（谁、何时、范围、行数）。
- **业务全量导出**（仅管理员，异步）：版本化格式（每资源一个 CSV + `manifest.json`，含 ID、外键、快照与事件表、行数与哈希）；**排除密码哈希、会话、MFA 密钥、平台与集成密钥**；用独立一次性导出口令加密；下载时重检权限；文件 24 小时后清理。与运维备份（含配置与密钥，`deploy/data.mjs:39`）明确区分。
- **退出测试**：用全量导出在空库重建客户—联系人—商机—合同—计划—收款关系并比对计数与金额。
- **财务对账导出**：按月分别列到账（按到账日）、已复核到账（按复核时间）、已核销、未核销、合同未收、逾期、期初余额，附有效凭据版本。
- **财务角色**：新增 `finance` 角色，权限仅限收款登记/复核/核销/期初确认/对账导出，保持录入与复核不同人；未实现前以 2 名管理员运行并在例外矩阵中签字接受风险。

### 4.11 账号安全（MFA）

- 老板、管理员、财务强制 TOTP；其他角色可选。
- 状态机：密码通过 → 受限令牌（只能访问 MFA 绑定/验证接口，5 分钟）→ TOTP 或恢复码通过 → 签发正常会话。强制用户首次登录必须先绑定。
- `runCommand` 与 HTTP 守卫校验会话的 `mfaSatisfied`；智能体委托只能由已满足 MFA 的会话创建。
- 验证码限速（每账号每 15 分钟 5 次）、同一时间步不可重放；恢复码 10 个，哈希存储，单事务原子消费。
- 重置：另一名管理员发起，需其本人再次 MFA；重置撤销该用户全部会话与智能体委托；审计。
- 全体管理员失去因子：安装机上的离线恢复命令（需主机访问 + 业务加密密钥），生成一次性重置码并审计；不提供普通密码重置绕过。
- 正式安装改为初始化 2 名管理员。

### 4.12 不做（试点期冻结）

售后/附件的后续扩展（SLA 自动升级、外发、客户门户、病毒扫描、对象存储）、财务扩展（开票、退款）、审批会签/加签、智能体扩展、免登与双向审批、多币种、邮件/日历同步。只修缺陷；它们在 G3 仍是商用门槛，见 §2.2。

### 4.13 售后与附件（PR #12、#13，纳入试点）

## 6. 架构

### 6.1 总体

```
Web(桌面 + 移动 4 页) ─┐
钉钉/飞书工作台 H5 ────┼─> 反向代理(TLS 终止) ─> NestJS API ─> 应用服务 ─> MySQL 8
MCP 客户端(现有边界) ──┘                              │
                                                     └─ OutboxEvent
Worker(同代码独立入口, runSystemCommand) ── 续费生成/提醒/待办摘要/预测锁定/外发投递
宿主机 systemd timer ── 现有加密备份脚本 → 本机 + 异机复制
```

- 不拆服务、不新增数据库；试点规模不引入 Redis。
- 现有 `apps/api/src/cron/*` 保持停用；新任务全部在 Worker，带 `JobRun` 租约与执行记录。
- **备份不放进 Worker**：现有脚本在宿主机调用 Docker Compose（`deploy/data.mjs:1,16–29`），由宿主机 timer 运行，避免给应用容器挂 Docker socket。

### 6.4 部署与运维

- **HTTPS 边界**：交付 `deploy/Caddyfile.example` 与 Nginx 示例；API 只绑定内部网络/localhost，外部只开放代理 443；API 只信任来自代理的 `X-Forwarded-*`。现有 localhost HTTP 安装与探活路径保留。放行条件为**入口实测**：HTTP→HTTPS 跳转、证书续期演练、外网直连 API 被拒、伪造转发头无效、健康检查可用。
- **定时备份**：宿主机 systemd timer 每日 02:00 调用现有加密备份；保留 14 天；异机复制（必选，目标在 P0 确定）；备份年龄 >26 小时、容量接近 128 MiB 上限、复制失败均告警；备份密钥与备份文件分开保管。
- **恢复演练**：试点前 1 次、第 3 周 1 次，在独立 Compose 项目执行，记录 RTO 并保存回执。
- **监控**：外部探测 `/health/ready`（Uptime Kuma）；错误跟踪（自建 GlitchTip 优先，默认过滤令牌、Authorization、联系人与财务字段）；Worker 心跳、外发积压、死信、备份年龄四类告警发给两名管理员。
- **恢复目标**：RPO ≤24 小时、RTO ≤4 小时。这意味着故障时可能丢失最多一天的已确认写入；成功标准写为“试点期未发生数据丢失事件”，而非承诺零丢失。若业务要求更低 RPO，另行评估 binlog 异机复制。

### 6.5 性能目标

测试条件：2 vCPU / 4 GB 应用 + 同规格 MySQL；单租户 50 用户、5 万客户、20 万跟进、2 万商机，按 10% 负责人持有 50% 数据制造倾斜；20 并发虚拟用户，混合 70% 读 / 30% 写，同时运行一个 5,000 行迁移发布；冷启动后预热 5 分钟再计量。

目标：列表/详情 p95 ≤500ms；今日待办 p95 ≤800ms；看板/周会 p95 ≤2s；错误率 <0.5%；迁移 5,000 行 ≤10 分钟；无死锁未重试成功。同时校验汇总结果与全量 SQL 计算一致（不能用“前 100 条”换延迟）。已知风险点：客户查重扫描全租户名称（`customer-policy.ts:6–19`）、看板全量加载（`workspace.service.ts:1202–1206`），需改为索引查询与数据库聚合。

### 6.6 个人信息保护

在收集任何真实素材前交付《试点数据处理说明》：

- 数据清单：联系人姓名、手机、邮箱、职务；合同与财务数据；名片与聊天记录（仅用于 P0 访谈分析，不入库）。
- 处理目的与合法基础（客户关系维护、合同履行）；最小字段；留存期限（试点结束后 30 天内按决策删除或转正式）。

- 受托处理：错误跟踪、云服务器、钉钉/飞书属于受托或第三方，按实际部署评估告知、委托协议与是否出境。
- 权利响应：删除/更正请求流程；与依法需保留的财务/审计记录冲突时，保留最小必要并标注。
- 事件处置：泄露时的通知与上报责任人。

## 10. 切换、回退与试点运营

1. **切换 runbook**：T−1 天彩排；T 日 18:00 冻结 Excel 写入 → 迁移发布 → 期初确认 → 对账单签字 → T+1 08:00 开放；冻结期间的新增记录登记在纸面清单，开放后补录。
2. **放弃切换条件**：对账差异无法在 T+1 12:00 前解释 → 回到 Excel，CRM 数据保留但标记“彩排”，不清库。
3. **试点中回退**：若在第 N 周决定停止，用业务全量导出交给销售团队，并按 §6.6 处理数据。
4. 培训：45 分钟 + 一页纸操作卡 + 首周每日 15 分钟答疑。
5. 节奏：周一周会用 CRM；周五主管看采用度；第 2、4 周复盘。
6. **事故分级**：S1 数据错误/丢失/越权 — 1 小时响应、停用相关功能、通知老板；S2 核心任务不可用 — 4 小时；S3 其他 — 下一工作日。修复走单独小 PR。
7. **责任矩阵**：迁移（管理员）、对账（财务）、规则（主管）、运维与备份（管理员 B）、证据独立复验（指定非构建方人员）。
8. 用户文档：`docs/USER_GUIDE.md`（试点范围内能用什么、怎么用、限制）。
