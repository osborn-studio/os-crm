# 通用审批会签 · 第一批

本批在原顺序审批、转审与人员交接基础上增加指定人员会签。同一个逻辑节点内2—8位明确指定的人员都同意后，才进入下一节点；任何一人驳回即终止整份申请。支持同一流程混合单人节点和会签节点，最多12个逻辑节点。没有“部分同意即通过”或自动跳过离职人员的规则。

## 配置与使用

1. admin进入“审批设计器”，创建或复制一个流程。在需要共同核对的节点选择“多人会签（全同意）”，从列表选择2—8位具备完整通过及驳回权限的有效人员。
2. 可以在会签前后添加单人、角色或部门负责人节点，保留金额条件及表单字段规则。多人角色不会被静默随机选取，需明确指定会签人员。
3. 保存草稿并预演，界面按逻辑步骤标出同组会签人员；确认后发布。发布新版本不会改写已发起审批的原参与人员和快照。
4. 申请从业务详情提交；通用表单从审批中心发起。申请人不能包含在自己的任何会签或单人审批节点中。合同、订单、立项等仍需从原业务入口提交，不能用通用表单绕过业务校验。
5. 同组每位参与人都会看到自己的待办，可以独立处理。首个同意只保存该人的意见；其余人未同意前，后续步骤不可处理，也不执行最终业务回调。界面中的多条同组待办不代表串行先后顺序。
6. 任意一人驳回，整份审批结束；其他尚未处理的意见保留为未执行历史，不能继续通过。申请人仍可依原规则撤回待审批实例。

## 转审与人员交接

当前会签成员可以转交本人尚未处理的意见；管理员可以恢复当前或后续尚未处理的分配。转交保留逻辑节点顺序、原人员/节点、原因及继任节点，不覆盖原流程快照。同一会签组不能转给另一位已同意或仍在等待的成员，避免一个人重复承担两份独立意见。

旧审批人在转交后不能继续投票，新人员接替当前组意见；后续节点转交仍不会提前激活。任何未结束审批中待办会阻止相关人员停用/离职/变更执行资格，须先交接；紧急访问撤销仍可重置密码。已经同意的意见保持历史，不因随后调岗自动改写或重新计票。

## 事务与证据

每次决定通过共享审批服务，在Serializable事务中重检实际会话/角色/企业、当前逻辑步骤、独立人员及意见状态；保存节点、父实例、站内通知、事件、幂等回执及审计。父实例版本单调推进。并发成员意见只能产生一个最终结果；同一请求重试不会重复意见、通知或业务回调。

最后一票与合同等业务回调在同一事务中执行。回调之后发生审计故障也会回滚最后一票和业务状态，之前已经提交的独立意见仍保留；故障排除后可以用原请求标识重试。新步骤只在前一组全员同意后一次性产生待办通知，不会因每个部分意见重复通知下一步骤。

流程快照中每位成员记录同一order和mode=all；单人节点mode=single。运行节点复用同一逻辑顺序，不改写原定义或既有转审历史。受影响能力契约升级2.0；读取流程/发起/撤回等未改变输入语义的契约保持1.0，HTTP接口仍可查询完整Schema。不开放代理审批写入，不向钉钉/飞书等平台外发。

## 安装与验证

增量迁移`202611010012_approval_countersign`仅在流程定义审批人类型枚举末尾追加users_all，既有顺序定义和运行节点不回填或改写。上线先备份旧版本及数据库，再迁移和启动新API/网页；不要把新会签定义交给不支持users_all的旧版本运行。需要退回旧版本时按旧版本备份恢复到新库验证，不能直接原地降级覆盖。

`pnpm check`及独立`SMOKE_ALLOW_WRITES=true node scripts/countersign-smoke.mjs`验证组内独立处理、非锚点成员、单人顺序兼容、转审、防重复意见、申请人/企业边界、并发同意与驳回、晚期故障回滚、合同最后一票原子回调、发布新版本不改旧快照，以及部分同意实例的加密恢复和恢复后继续处理。测试只允许独立tb_crm_test_*合成数据库，不是客户签收或第三方平台联调。
