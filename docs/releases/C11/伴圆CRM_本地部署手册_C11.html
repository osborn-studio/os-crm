伴圆CRM 本地部署与升级恢复手册

C11 · 2026-11-01 工程候选。源码公开、可本地安装；演示与合成测试结果不等于客户验收或生产上线。应用包版本仍为0.2.0-demo.2，以本包源码提交及迁移记录识别工程版本。

总包与环境

解压完整包后先核对MANIFEST.json的sourceCommit和SHA256SUMS.txt。01_安装源码/tb-crm含源码、冻结锁文件、15个迁移、种子、部署脚本及预构建API/网页；不含Node、MySQL、Docker镜像、node_modules或本机.env，因此不是离线安装包。首次联网下载工具、镜像及依赖。

推荐独立测试机或测试虚拟机。Docker入口需要Docker Engine/Desktop与Compose v2；本机原生模式需要Node24、pnpm11.25.0和MySQL8.4，不能把旧本机数据库地址直接复制给别人。包内预构建内容用于便捷核对，Docker仍从源码冻结依赖构建。

演示Docker安装

macOS/Linux终端设置export SEED_ADMIN_PASSWORD=12345，运行sh deploy/start.sh；Windows PowerShell设置$env:SEED_ADMIN_PASSWORD='12345'并运行./deploy/start.ps1。脚本生成独立随机基础密钥到deploy/.env，首次初始化四角色与演示数据；后续重启保留业务和密码。

打开http://localhost:3000，四账号admin、manager、sales、boss。端口占用时调整本机配置WEB_PORT；默认只绑定127.0.0.1，数据库不映射公网。只读检查node --env-file=deploy/.env deploy/verify.mjs。

停止用docker compose --env-file deploy/.env -f deploy/compose.yml down，不添加删除卷选项。新副本使用独立Compose项目、端口与数据卷，不删除旧卷。

原生演示安装

安装Node24与pnpm11后执行pnpm install --frozen-lockfile。参照.env.example在本机生成独立配置并创建专用空库，设置SEED_ADMIN_PASSWORD=12345；不要将.env提交Git。依次pnpm db:migrate、pnpm demo:seed、pnpm build、pnpm demo:start，默认网页3000、API4000。迁移或种子失败时先检查本机数据库账号权限，不将已有正式库用作演示库。

本机启动演示.command是原生启动便捷入口，不负责为陌生电脑安装Node/MySQL。首次配置后才可双击。macOS本机Node24/MySQL8.4路径有实际验证，其他操作系统原生路径仍需实机验收。

正式安装与恢复基础候选

本入口从空库安装企业环境，区别于 deploy/start.sh 演示入口。它尚未完成商用验收，功能边界及后续批次见 建设计划。已发布的演示密钥和数据库快照继续作为公开演示资料保留，正式环境使用此入口生成全新独立配置。

首次安装

需要 Docker Engine/Desktop、Compose v2；首次需联网。备份恢复宿主机另需 Node.js 24。

macOS/Linux：

export TENANT_CODE=MYCOMPANY
export TENANT_NAME='我的企业'
# 自行设置唯一的管理员密码：12至72位，含大小写字母和数字。
# 支持的符号：! @ # % ^ * + _ . -
export SEED_ADMIN_PASSWORD='替换为自己的强密码'
sh deploy/start-production.sh

Windows PowerShell：

$env:TENANT_CODE = 'MYCOMPANY'
$env:TENANT_NAME = '我的企业'
$env:SEED_ADMIN_PASSWORD = '替换为自己的强密码'
./deploy/start-production.ps1

示例中的中文提示不是合格密码，必须自行替换。配置写入被 Git/Docker 忽略的 deploy/production.env；已存在文件不覆盖。数据库口令、JWT、业务加密密钥和备份密钥分别随机生成。企业名称不支持引号、反斜线、美元符号或井号，防止跨平台环境文件解释不一致。

默认网页绑定 127.0.0.1:3000，数据库不映射宿主端口；与演示系统同时运行时先设置不同的 WEB_PORT 和 APP_URL。从本机打开地址，输入安装时的企业编码、管理员用户名（默认 admin）及自行设置的密码。初始化只创建企业、四种角色、管理部、管理员、公海和商机阶段，不创建演示客户、合同或财务记录。重启不修改用户、密码或业务数据。

node --env-file=deploy/production.env deploy/verify-production.mjs --expect-empty

这条验收命令只读取；--expect-empty 仅首次空安装使用。正式外部访问应通过 HTTPS 反向代理连接本机端口，并设置 HTTPS 的 APP_URL；本入口不会配置域名、证书或公网端口。人员与会话操作见 人员管理说明。

加密备份

node --env-file=deploy/production.env deploy/data.mjs backup backups/company-20261101.crmbackup

备份通过 MySQL 事务一致性导出，包含表结构、数据、迁移历史和应用恢复所需配置，再压缩并以独立 BACKUP_KEY 用 AES-256-GCM 加密认证。不会覆盖已有备份。文件与目录以仅当前用户访问权限创建；第一版 SQL 导出上限为 128 MiB。此方案需要保持备份时不运行数据库迁移等 DDL。

单独离线保管 BACKUP_KEY 和配置文件，至少将加密备份复制到另一台设备。备份文件本身不包含备份密钥。遗失密钥无法解密恢复。C10私有证据文件以二进制保存在数据库，随本备份包含元数据及原件；旧原型文档路径不等于实际文件，不会据此虚构原件。

恢复演练

node --env-file=deploy/production.env deploy/data.mjs restore backups/company-20261101.crmbackup tb_crm_restore_drill

恢复先完整验证密钥、认证标签、格式、SQL 校验值及 schema 指纹，再创建全新 tb_crm_restore_* 数据库并导入。已有目标库直接拒绝，不删除、不清空、不覆盖原库。导入失败时保留未推广的目标库，修复原因后使用另一个新库名重试。

成功时在备份旁生成 .receipt.json 和 .env，记录恢复时间、源与目标库、关键表的行数及配置路径。恢复配置保留备份中的业务加密密钥，以读取原来加密的内容；使用当前服务器数据库口令，重新生成 JWT 签名密钥使旧会话失效。不自动切换运行中的系统。

请先在独立 Compose 项目和端口验收恢复库。正式切换前停止应用写入、保留当前配置和原库、另做一次备份，并核对用户、客户、合同、应收余额、审批和审计；切换时人工将验收通过的恢复配置作为新的配置文件运行相同 Compose 项目。恢复配置不含原卷，必须在实际恢复的 MySQL 服务器上使用。更换 Compose 项目会创建独立数据库卷，必须另外导入备份，不能只复制环境文件。

# 在当前数据库服务中切换到已经验收的恢复库；只有操作人员完成验收后执行。
# docker compose --env-file backups/company-20261101.crmbackup.tb_crm_restore_drill.env -f deploy/compose.production.yml up -d --wait

schema 指纹不一致时先用备份对应的源码版本恢复并验收，再运行经过测试的升级迁移。不要用旧数据库覆盖已升级中的正式库。当前未实现自动调度备份、跨版本自动回滚或高可用；这些属于后续商用验收范围。会签定义需要支持users_all的同版API；不可将旧API直接连接已配置会签的新库。

已有库升级检查单

记录当前源码、迁移和配置，停止写入并创建可恢复备份；在独立副本验证后，停止旧API，应用随包增量迁移，再启动同版API和网页。不要对已有企业重放演示种子。先检查ready，再重新登录四种适用角色，核对客户/合同/余额、旧审批、会签、附件及历史。

C11仅向枚举末尾追加users_all，旧审批不回填或改写。新定义不能交给不支持会签的旧API；退回旧代码时从旧版本备份恢复新库验证，不能原地降级覆盖当前库。C10附件随SQL备份保留原件与摘要；恢复后抽查下载Hash。保留原库，不自动提升恢复库为生产。
