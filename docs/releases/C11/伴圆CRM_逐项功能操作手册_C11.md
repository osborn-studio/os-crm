# 伴圆CRM 逐项功能操作手册

C11 · 2026-11-01 工程候选。源码公开、可本地安装；演示与合成测试结果不等于客户验收或生产上线。应用包版本仍为0.2.0-demo.2，以本包源码提交及迁移记录识别工程版本。

## 如何阅读与操作
本手册对应当前前后端。按钮按角色、记录范围和状态出现，未出现按钮不代表账号故障。列表搜索后打开详情，核对客户、编号、状态和更新时间，再提交操作。金额以人民币及十进制表示；业务日期按界面日期输入，事件时间显示北京时间。

提交超时先刷新详情及历史，核对是否已成功；不要为了重试盲目创建第二条业务。API写入携带requestKey，修改或动作携带expectedUpdatedAt；版本冲突应重新读取、核对后再提交新请求。同一请求号不能更换输入。字段不接受调用者指定企业或操作人。

### 四种角色
|角色|演示账号|默认业务范围与责任|
|---|---|---|
|管理员|admin|本企业组织、账号、集成、审批设计及管理；财务台账写入|
|销售主管|manager|本部门销售数据、归属安排、项目管理；仅处理分配到的审批|
|销售|sales|本人销售与有明确职责的交付记录；公海受限摘要；发起业务|
|老板|boss|企业经营读取；可处理分配到本人的审批，业务编辑默认关闭|

四个公开演示账号密码均为12345，仅用于隔离演示企业。空企业正式安装不会创建这四个演示用户，管理员设置独立强密码并新建人员。老板不是通用超级管理员，审批权限也不等于财务或项目验收权限。

### 首页、通知与审计
经营驾驶舱按当前可见数据汇总，点击指标可下钻；合同额、计划应收、已收、剩余分别查看，不能等同营业收入、利润或银行余额。销售管道按商机阶段展示，与列表共享数据。
站内通知从右上入口读取并打开相关业务，详情仍重新检查权限；通知出现不代表钉钉、飞书或邮件已送达。业务审计保存操作及结果，不显示密码、令牌或附件正文。旧版本未记录的历史不会补造。

# 客户导入、销售归属交接与合同变更

这是 C3 第一批核心路径，仍为商用建设候选。复杂主体合并、批量离职任务交接、已执行合同的下游变更/冲销将在后续批次补齐。

## 客户导入

管理员进入“客户经营 → 客户导入 / 销售交接 → 客户导入”。下载模板，以 CSV UTF-8 保存；可选择文件，也可粘贴带表头的 CSV 文本。

允许的列：客户名称、行业、级别、地区、地址、官网、备注。客户名称必填，其他列可省略；不接受负责人、企业编号、银行资料等额外列。每次最多200条、1MiB，支持带引号的逗号、换行及双引号。级别使用重点客户、普通客户、潜在客户。

1. 预检数据：列出可导入、重复跳过、错误需修正的记录，不创建业务客户。
2. 规范化名称查重：统一全半角、去空白和大小写；同时检查已有名称和文件内重复。它不等于模糊主体识别，不自动合并企业。已有历史重复记录保持原样，后续需要专门的主数据合并方案。
3. 有错误时先修正并重新预检。预检15分钟有效，限同一企业与操作者提交。
4. 点击明确标注“导入N条、跳过重复M条”的确认按钮。新客户全部进入公海，不自动改动已有客户。
5. 提交时再次检查额度和重复；预检后已有同名客户创建时整体拒绝，不写入一半。相同请求重试返回原回执，并发提交同一预检只成功一次。

回执记录导入数量、跳过数量、客户编号和原始内容摘要，用于追溯。成功导入后按正常业务分配和维护，不提供会抹去后续业务的一键物理删除。普通新建、改名和线索转化使用相同名称约束；查重失败不返回不可见客户的编号或负责人。规范化名称检查还保留已删除历史名称，避免悄悄重建相同主体。

## 销售归属交接

管理员或销售主管打开同一页面的“销售归属交接”。主管可以查找本部门有效、停用或离职人员名下的客户；列表最多显示100条，使用名称搜索定位其他记录。接收人须为有效销售，主管只能在本部门范围内交接。存在其他部门销售负责的关联业务时需管理员处理。

选择客户、接收销售，填写原因，先预检再确认。预检列出商机、合同、订单、项目销售归属、已转化线索和原销售未完成行动的数量；提交校验客户版本和整个关联范围摘要。预检后任何关联范围变化都需要重新预检。

确认后同一事务完成归属更新和私海持有记录迁移。联系人和跟进关联随客户保留，历史作者不改写；项目经理、项目任务执行人和历史审批申请人不自动替换。项目交付人员交接属于 C4，审批转审属于 C6。

有关联销售业务的客户不能再用旧版单独分配、直接退回或普通领取绕过整体交接。合同、订单、立项或合同变更审批处理中时先完成或撤回审批。旧销售不再通过销售归属读取相关客户/商机/合同；若同时是原项目经理，其独立交付身份不因销售交接自动消失，历史自行创建的线索仍按历史权限读取，但已转化线索不可改写。

## 报价版本与合同引用

商机报价仍从“商机与报价”操作。每次报价用 Decimal 重算数量×单价与合计，生成不可改写的历史版本。商机详情的“报价历史版本”可展开查看当时产品名称、数量和价格，后续产品改名不覆盖旧快照。

关联已有报价商机创建合同时，金额须与当前选用报价一致，并保存版本和产品快照。后续商机再报价不会漂移已保存合同；仅修改草稿合同条款保留原报价版本。明确改价并与最新报价一致时才更新合同选用版本。旧演示版本没有留下的历史报价不会被虚构补齐。

正式安装的销售可创建、编辑本人范围内草稿、提交合同审批，以及在审批通过后签约；主管范围仍按部门过滤，老板仍只读业务并处理分配到的审批。升级仅为原本已有合同创建/读取权限的内置销售补充这一合同操作权限，不对已主动剥离的角色授权。

## 合同变更与终止

管理员先在审批设计器配置并发布“合同变更 / 终止”流程，指定其他合格审批人。自定义必填字段会在发起变更时出现；系统保留的审批金额与证据字段不能作为自定义字段编码。

合同列表 → 合同变更/记录 → 发起变更/终止，可申请金额/税率、日期、付款条款变更或终止。填写原因及凭据说明，预检影响与审批表单，核对前后值后提交。原合同在申请时不会提前变更，审批人能看到服务端固定的前后对照，不能用自填表单伪造金额快照。

本批明确只允许：已签约或执行中、没有订单/项目/发票/核销、仅一笔未拆分且未执行回款计划的合同。已有下游业务时拒绝直接改写，需后续变更/冲销对账闭环；不会静默修改已交付订单或已收款余额。

批准后在同一事务更新合同、金额/税额、未执行回款计划及客户有效合同统计。终止会取消未执行计划并将剩余金额归零，保留历史合同原金额、申请和审批记录。该业务状态不代替外部签署、法律手续或退款处理。

驳回保留原合同，撤回把变更标为已撤回并解除处理中限制。源合同在审批期间有其他版本变化时，批准整体失败，审批节点也回滚为待处理；申请人应撤回后重新预检，不覆盖其他人的修改。一个合同不能同时有两项待处理变更，处理中不能新建下游订单或项目。


# 项目交付、验收与整改（C4 第一批候选）

本说明覆盖订单审批、确认、交付及合同生成项目后的执行主线和人员交接。后续C8售后工单、C10私有附件已另有操作说明；订单分批发货、取消补偿、大文件对象存储仍未实现，不能作为整套商用验收结论。

## 执行顺序

1. 已签约合同生成项目，或填写客户、起止日期新建项目；提交立项审批并通过。
2. 项目经理或具有该项目范围权限的主管/管理员启动项目。未启动、未批准或已关闭项目不能创建、修改或执行任务。
3. 在项目任务中新建任务，选择项目及可选的关联里程碑。只能关联该项目未完成的里程碑；未关联任务在最终交付里程碑前统一检查。新任务由创建人执行，项目经理或有范围权限的主管可从任务列表转派。
4. 开始任务时填写工作说明；完成任务填写结果/依据及累计实际工时（0.1—9999.9小时，最多一位小数）。工时为本任务累计值，整改完成时填写新的累计值，不是追加扣费、工资核算或完整工时单。已完成任务不可直接改写。
5. 从项目推进当前里程碑，填写交付结果和依据。系统按顺序检查当前里程碑关联任务；最终交付还检查未关联任务。不允许跳过未完成任务。里程碑及任务记录在同一事务保留操作者、时间、说明及工时等证据。
6. 全部里程碑和任务完成后提交验收，填写本次验收材料说明。验收处理中冻结任务创建、编辑、执行与里程碑推进，防止依据漂移。
7. 另一名有项目范围权限的主管或管理员确认验收，或填写拒收及整改要求。项目经理和提交人不能确认本人项目；老板仍保持业务只读，不能通过本入口代替主管。至少需要另一位合格复核人，单管理员不能自验收。

## 拒收与整改

拒收后项目保持进行中，验收状态显示已驳回。项目经理或有项目范围权限的主管可以对已完成任务“发起整改”，必须说明整改内容。

系统重新打开该任务所属里程碑及其后续里程碑，重算进度；未绑定里程碑的任务重新打开最后一个里程碑。整改不删除历史完成、工时或验收记录。任务重新开始并完成后，按顺序重新确认里程碑并提交验收。拒收也可针对验收材料补充，允许保留已完成任务并以新的说明重新提交。

最终确认后项目进入已完成，阶段关闭，记录验收日期、结束日期与结项说明；不能再从任务入口改写交付。已通过新版验收的项目可进入独立售后工单流程，工单不重开或改写原项目验收。

## 查看记录与权限

项目详情的“交付与验收记录”展示启动、任务执行/整改、里程碑及历次验收决定。任务详情只展示该任务的记录。接口返回最近100条事件；完整历史保留在本地数据库，分页导出后续提供。C10增加受控PDF/PNG/JPEG附件及不可变文件摘要快照，详见PRIVATE_ATTACHMENT_OPERATIONS；仍不提供外部客户签署或电子签章。

网页、HTTP 和现有只读 MCP 共用 WorkspaceService。`/workspace/schema` 的项目/任务操作契约升级为2.0，列明必填说明、工时与版本参数；身份来自认证上下文，写入执行实时会话/权限重检、租户/记录范围、Serializable事务、幂等和乐观版本检查。审批与任务的事件均不开放独立写入入口，智能体写操作仍未开放。

## 升级

先备份，应用增量迁移 `202611010003_delivery_acceptance`，再启动匹配的新前后端。新增项目验收状态和交付事件表，不删除原数据、不重设账号。

迁移前已完成项目标记“历史完成（无新版验收记录）”，不补造验收事件；旧项目仍保留实际状态。未完成旧项目开始采用新的任务、里程碑和双人验收规则。操作请求升级为2.0后，旧客户端直接点击验收或无说明完成任务会被拒绝，需使用新版页面。

可靠外发通知、完整工时单、跨项目批量交接、订单与项目取消补偿和生产容量测试仍待后续批次。私有文件权限及内部售后已分别由C10、C8提供。没有把文本或文件记录当作客户外部签署。

## 人员交接增量

项目列表 → 交接项目经理：管理员或主管选择接收人并说明原因。系统同事务交接项目经理、原经理名下未完成任务及其负责的未完成里程碑；其他执行人的任务、已完成任务的执行人、创建人及历史证据不随之改写。审批或验收处理中及已关闭项目不能交接。

任务列表 → 转派任务：项目经理或有项目管理范围的主管选择接收人，填写待办及原因。普通执行人不能自行转派，已完成/取消任务不能转派。验收处理中不可转派。

接收人必须为本企业有效账号、有效部门，并具备适用角色及项目读写权限；主管及项目经理限定适用部门，管理员可明确安排跨部门协作。任务接收人仅在持有未完成任务时获得项目读取，不获得项目管理或他人任务管理权限；完成后若无其他归属则收回这一项目读取范围，自己的历史任务仍可查看。项目经理交接不改变销售负责人及客户归属，原经理如仍为销售负责人仍可按该职责读取项目。

账号停用、离职、调岗或移出适用交付角色前，会检查未结束项目经理职责及未完成交付任务，有未交接工作则拒绝。紧急撤销访问可由管理员先重置密码，业务随后交接；不会为交接自动启用旧停用账号。

正式安装销售缺少订单/项目继续操作权限的问题通过`202611010004_delivery_responsibility`修复：只对已有读/创建路径的内置销售补齐相应更新权限，未配置创建权限的角色不扩权。新安装使用修复后的默认定义，仍受本人/团队、项目职责及状态限制。迁移后重新登录。

候选人员列表最多200人；批量离职交接、复杂项目团队和完整跨部门协作权限配置仍待后续。交接事件保存当时操作者姓名、目标人员及转移数量，网页时间明确显示北京时间。

独立3012合成站已读取核对交接入口、影响说明、有效接收人及交接原因必填字段，未在网页最终转派权限。实际交接、访问变化及停用由真实HTTP/MySQL集成检查执行。另修复未绑定任务整改时的阶段显示：始终回到最早未完成里程碑，避免进度为0却显示验收阶段。




# 本地收款登记、核销与更正（C5 / C5.1 候选）

本批支持人民币银行转账凭据的人工登记、另一管理员复核、分摊核销、撤销核销及作废。系统只维护本地业务台账，不拉取或核验银行流水，不发起转账、退款、税务开票或会计凭证。发票、总账及外部对账仍为未开放功能，整套系统尚未商用验收。

## 使用前提

- 企业至少有两位有效管理员：一人登记，另一人核对凭据。管理员可在人员管理创建第二个管理员；正式账号使用独立强密码，不设置共享演示密码。
- 销售、主管、老板仍仅按原有本人/团队/企业范围读取财务数据，本批不额外授予财务写权限。所有写入口仅管理员可用。
- 合同已经签约，回款计划合计、已收、剩余金额及有效核销明细一致。合同变更审批中不能核销。
- 历史演示或外部导入记录保持只读，不自动变成本批可写台账，不根据演示数字伪造复核或银行证据。

## 登记与独立复核

财务中心 → 收款登记与核销 → 登记收款，选择客户、填写凭据金额、到账日期、外部到账凭据编号和登记说明。可选绑定合同，绑定后只允许该合同的回款计划核销；不绑定合同则可在同一客户的不同合同计划之间分摊。

金额以十进制文本传输，最多13位整数及2位小数，必须为正数；目前仅人民币，不提供币种或汇率转换。日期为有效YYYY-MM-DD。凭据编号最多50字，执行NFKC全角规范化及首尾空白去除；大小写保留，重复编号含已作废历史一律拒绝。已知历史记录中的相同编号也会阻断；历史未保存编号的记录无法自动查重，复核人仍需核对原始材料。

登记后为“待独立复核”，金额和客户等信息不允许直接改写。另一位管理员登录后核对凭据，再填写复核说明并确认。登记人本人不能复核；前端禁用本人记录的复核按钮，服务端再次检查身份。没有自动银行鉴权或自动到账确认。

## 分摊核销

已复核收款 → 核销，选择同客户计划和本次金额，核对收款可用余额、计划剩余及处理依据后提交。

系统在同一Serializable事务检查：

1. 当前用户/企业/会话和管理员身份有效，收款为本批登记且已复核。
2. 收款、计划及合同属于同一企业、同一客户，且满足可选合同绑定。
3. 收款与计划版本没有变化，合同没有待处理变更，计划未取消。
4. 收款已核销等于有效明细之和，未核销余额正确；每个计划的已收、剩余及合同合计一致。
5. 本次金额不超过收款可用余额或计划剩余。

提交后同步更新收款已核销/可用、计划已收/剩余与状态、合同累计已收/剩余，并保留核销记录、前后金额、操作者、依据、命令回执及审计。同一收款可多次分摊到同一计划，每笔单独留痕。并发争抢同一收款或计划只有符合当前版本及余额的请求可成功。

发现旧账不平时拒绝操作，不静默重算或抹平差异。需先核对原始记录，不能通过修改浏览器金额绕过。

## 撤销核销与作废

已复核收款 → 撤销核销，选择一笔有效核销并填写原因。第一版整笔撤销该核销，不提供部分撤销。原记录标记已撤销，保留时间、操作者和原因，余额同事务退回到收款、计划和合同。重复或并发撤销不能重复恢复余额。之后可重新分摊，生成新的明细，原历史不删除。

**撤销核销不代表退款**，不会向银行发出任何付款指令。

全部有效核销撤销后，可作废收款登记；待复核收款也可作废。作废后金额原值保留，可用余额为0，不能复核或核销；编号仍占用，防止同一到账凭据重复入账。需更正内容或重新开立时使用下述显式流程，不伪造新凭据编号绕过去重。真实退款与会计冲销仍未实施。

## 登记更正与同凭据重开

1. 管理员从当前登记点击“更正 / 重开”。若已经有后续更正，先从“记录”的凭据链进入当前登记。历史演示/外部导入记录不能直接转为可更正台账。
2. 先撤销全部有效核销；原合同审批变更处理中也需先完成或撤回。核销撤销不触发退款。
3. 修改客户、合同绑定、金额或到账日期，填写更正原因。须明确选择有效合同或清除绑定。原凭据编号不能修改；更正后的合同必须与客户一致并满足签约、余额和审批守卫。原绑定合同已经终止时，可以明确解除绑定，但不能继续向该终止合同核销。
4. 确认后系统在一个事务中作废原登记、创建同凭据的新待复核登记、推进凭据当前指针，并为两张记录保留前后对照和更正原因。原客户、合同、金额、日期、复核人、已撤销核销与原作废说明保留；不会覆盖成新值。
5. 新登记的录入人为本次更正管理员，复核状态清空，需另一管理员重新核对确认。更正人不能复核本人新登记；原登记人可以复核由另一人更正的新登记，仍保持本次录入与复核分离。

普通重复登记始终拒绝同一凭据。原登记永久保留唯一凭据指纹，另用凭据主记录指向唯一当前登记；更正不会释放编号或同时产生两张可用登记。已作废且没有后续更正的当前记录，可填原因按相同内容重开；未作废记录若内容没有变化则拒绝。多次更正形成可导航的链，不能从中间历史版本分叉。

更正并发、陈旧版本、跨企业引用或写后事件失败时，整个更正回滚，不留下孤立新登记、错误指针或成功回执。更正不改变此前撤销后的合同、计划余额；新登记必须重新复核后才可核销。

管理员与老板可按企业权限读取完整更正审计链，老板仍不能写入。销售和主管按原有记录范围读取；更正对照、跨客户原因、原始备注中的更正说明与链路指针不会通过另一客户的旧记录泄漏。网页、HTTP 与只读MCP使用同样的投影规则。

本流程只在同一实际银行凭据下更正登记分类和内容，不支持修改原银行凭据编号、合并不同银行凭据、真实退款或会计冲销。编号本身录错时保留错误登记及作废依据，再按真实有效凭据独立登记；跨凭据关联更正与合并后续提供。

## 查询、AI与边界

台账展示收款最近100条，明细及事件各最近100条，计划最近100条。历史完整保留在数据库；大规模分页、导出和账龄报表后续提供，当前列表不是全量汇总。客户/合同下拉也限最近100个可见对象。

处理记录显示北京时间、当时操作者姓名、依据及核销前后余额。原财务列表只读；税务开票、会计、银行、退款、完整财务期结和数据迁移更正仍未实施。

`/finance-ledger/schema` 提供版本化能力ID、输入输出schema、权限、效果、状态与证据。身份及企业只能来自认证上下文，写入共用持久幂等、版本、事务、会话重检和审计。既有只读MCP `workspace.get` 可按当前范围读取收款核销/撤销及财务事件；本批未增加智能体写工具或独立财务委托身份，未调用大模型。

## 升级与恢复

先备份，依次应用`202611010005_receivable_ledger`及`202611010006_receipt_corrections`，再启动匹配的新前后端。新增财务事件、收款管理标识/凭据指纹、核销撤销字段、更正前驱和凭据主记录；历史核销初始仍为有效，旧演示/外部收款保持不可写。不删除旧核销，不回填虚构到账编号。

更正迁移只为C5已经登记、具有指纹的台账建立原始/当前凭据关联，包含已作废记录；不把旧外部记录标为可写，不伪造复核或更正事件。已用上一版实际建立非空收款后执行升级检查，并验证更正链、凭据占用、事件及新待复核状态能经加密备份恢复到新库，旧会话不能访问恢复副本。

新核销支持同一收款/计划多笔历史，不能把旧版代码直接连接升级后的数据库；跨版本回退需按原版本备份恢复到新库并验证，不覆盖当前账。附件、自动银行/税务联调、独立财务角色和授权及全部商用验收仍待后续。


# 审批设计、发起与日常处理
管理员进入审批设计器，创建流程并选择业务类型；业务单据用专属入口，通用事项可在审批中心发起。配置文本、数字、日期等字段及必填规则；保留字段不能冒用。按业务配置金额条件、节点名称及顺序，审批人可为指定人员、唯一可解析角色、部门负责人或多人会签。

先保存草稿并预演，检查匹配条件、每个节点实际人员、申请人是否冲突；确认后发布。已发布定义修改生成新版本，原申请保留发起时的表单、流程及人员快照。角色解析多人时须明确指定，系统不会随机选一个人；缺少合格人员时阻止发起。

申请人在业务详情提交或审批中心填写通用表单。审批人进入待我审批核对原始业务及字段，再填写意见通过或驳回；不能越过当前节点。申请人可按状态撤回待审申请。审批通过只触发该业务配置的回调，不代表银行到账、外部合同签章或客户签收。列表可以继续加载历史，处理记录保留原人员及意见。

# 审批转审与人员交接

当前支持顺序及C11会签待办的转审与管理员恢复；会签规则见下一节。尚不包括加签或第三方外部审批。转审只改变后续处理人，不代表审批通过，也不触发合同、订单或立项的业务回调。

## 日常转审

1. 打开审批中心，在“待我审批”选择“转审”，或者进入申请详情的“节点与交接”。
2. 选择具备审批通过和驳回权限的有效人员，填写原因。申请人、原审批人、其他企业、停用账号或停用部门人员不能接收。
3. 确认后，原节点标为“已转交”并保留原审批人、原因和处理时间。新节点继承原节点的顺序和名称，审批状态仍为待处理。
4. 当前节点转交后，原审批人不能再审批。新审批人收到站内通知，在“待我审批”处理；原审批人可在“我参与的审批”回看历史。
5. 接收人通过或驳回时，执行原有业务回调；申请人仍可撤回待处理申请。拒绝或撤回后不能继续转审。

候选人员每次扫描100人，并过滤实际权限；大企业可继续“加载更多候选人员”，即使某一页没有符合权限的人，也不会把仍有后续游标误报成结束。审批历史、审计事件每页50条，使用稳定编号游标加载，未把前50条当成全部历史。

## 离职、调岗与管理员恢复

管理员打开“企业审批与交接”，进入申请详情。管理员可以转交当前或尚未轮到的待审节点；普通审批人只能转交当前轮到自己的节点。后续节点转交不跳过当前节点，新接收人要等流程轮到该节点才能审批。

先转交该人员全部未完成节点，再到人员管理停用或调岗。尚有待处理审批时，人员管理仍拒绝停用或改变权限。紧急撤销访问可先重置密码，之后由管理员恢复待审流转。转审不会授予接收人新角色，也不会移交项目、客户或其他业务所有权。

## 历史与隔离

流程定义快照和业务表单不会随转审改写。处理事件额外保存操作者姓名、原/新审批人姓名、节点编号、节点顺序、原因，以及是否属于管理员恢复。原节点、转交节点和多次转交均保留。

申请人、曾被分配节点的参与者可以查看该申请及历史；管理员可在本企业内审计，其他人员和其他企业不可读取。这里采用“审批参与人能读完整申请”的策略，尚无字段级保密表单。旧审批不补造审计事件，原有节点处理记录照常可读。

## 事务和恢复

审批版本、当前会话及权限、节点状态、目标账号和部门、角色权限均在同一可串行化事务内重检。持久化请求标识支持相同请求回放；重复使用同一标识却改变参数会拒绝。并发转交不会分叉，转审与审批决定只有一个成功。

原节点、新节点、当前指针、审计事件、站内通知和命令回执原子提交；事件或通知写入失败时全部回滚。站内通知以数据库提交为准，不把外部请求发出当作送达。本批不发送外部消息；钉钉、飞书、邮件重试队列仍待建设。

迁移`202611010007_approval_events`只新增事件表，不改旧审批或审批节点。真实MySQL检查包含已有流程转审、合同回调、账号交接、并发、故障回滚、分页，以及加密备份到新库恢复后认证读取。恢复保留节点、事件、通知和命令，轮换会话签名，不覆盖或自动切换原库。


# 通用审批会签 · 第一批

本批在原顺序审批、转审与人员交接基础上增加指定人员会签。同一个逻辑节点内2—8位明确指定的人员都同意后，才进入下一节点；任何一人驳回即终止整份申请。支持同一流程混合单人节点和会签节点，最多12个逻辑节点。没有“部分同意即通过”或自动跳过离职人员的规则。

## 配置与使用

1. admin进入“审批设计器”，创建或复制一个流程。在需要共同核对的节点选择“多人会签（全同意）”，从列表选择2—8位具备完整通过及驳回权限的有效人员。
2. 可以在会签前后添加单人、角色或部门负责人节点，保留金额条件及表单字段规则。多人角色不会被静默随机选取，需明确指定会签人员。
3. 保存草稿并预演，界面按逻辑步骤标出同组会签人员；确认后发布。发布新版本不会改写已发起审批的原参与人员和快照。
4. 申请从业务详情提交；通用表单从审批中心发起。申请人不能包含在自己的任何会签或单人审批节点中。合同、订单、立项等仍需从原业务入口提交，不能用通用表单绕过业务校验。
5. 同组每位参与人都会看到自己的待办，可以独立处理。首个同意只保存该人的意见；其余人未同意前，后续步骤不可处理，也不执行最终业务回调。界面中的多条同组待办不代表串行先后顺序。
6. 任意一人驳回，整份审批结束；其他尚未处理的意见保留为未执行历史，不能继续通过。申请人仍可依原规则撤回待审批实例。

## 转审与人员交接

当前会签成员可以转交本人尚未处理的意见；管理员可以恢复当前或后续尚未处理的分配。转交保留逻辑节点顺序、原人员/节点、原因及继任节点，不覆盖原流程快照。同一会签组不能转给另一位已同意或仍在等待的成员，避免一个人重复承担两份独立意见。

旧审批人在转交后不能继续投票，新人员接替当前组意见；后续节点转交仍不会提前激活。任何未结束审批中待办会阻止相关人员停用/离职/变更执行资格，须先交接；紧急访问撤销仍可重置密码。已经同意的意见保持历史，不因随后调岗自动改写或重新计票。

## 事务与证据

每次决定通过共享审批服务，在Serializable事务中重检实际会话/角色/企业、当前逻辑步骤、独立人员及意见状态；保存节点、父实例、站内通知、事件、幂等回执及审计。父实例版本单调推进。并发成员意见只能产生一个最终结果；同一请求重试不会重复意见、通知或业务回调。

最后一票与合同等业务回调在同一事务中执行。回调之后发生审计故障也会回滚最后一票和业务状态，之前已经提交的独立意见仍保留；故障排除后可以用原请求标识重试。新步骤只在前一组全员同意后一次性产生待办通知，不会因每个部分意见重复通知下一步骤。

流程快照中每位成员记录同一order和mode=all；单人节点mode=single。运行节点复用同一逻辑顺序，不改写原定义或既有转审历史。受影响能力契约升级2.0；读取流程/发起/撤回等未改变输入语义的契约保持1.0，HTTP接口仍可查询完整Schema。不开放代理审批写入，不向钉钉/飞书等平台外发。


# 售后服务工单 · 第一批候选

这是内部售后服务台。只允许已通过新版独立验收、状态为已完成的项目提交工单；历史“已完成但无新版验收”项目不能跳过验收直接进入售后。工单不修改原项目验收、财务余额或合同。

## 操作

1. 在“项目交付 → 售后服务工单”点击“提交工单”，选择有权读取的已验收项目，填写标题、优先级、问题与复现步骤。
2. 项目经理、项目经理所在部门主管或管理员指派接收人。接收人必须是本企业有效账号、有有效部门及项目读写执行权限；非管理员只能选择相应部门人员。
3. 当前处理人点击“开始处理”，随时追加处理记录，再提交解决方案和验证结果。
4. 另一位有该项目管理权限的人核对记录后关闭。解决人即使是管理员也不能自己关闭；老板角色只读。
5. 复核不通过可退回；关闭后也可带原因重开。原解决方案与解决人保留在历史事件中，当前方案清空，重新处理并提交。退回/重开时按新指派同样的规则重验原处理人（在职、部门有效、具备执行权限）；不合格则回到待指派（open），由管理人重新指派。
6. 未解决前可转派；转派回到已指派状态，新处理人开始处理。取消必须提供原因，取消后不再开放修改或重开。没有删除工单/历史的接口。
7. 离职、停用、调部门或取消执行权限前，需转派其所有未关闭/未取消工单。紧急撤销访问仍可重置密码，避免为了交接继续保留旧会话。

指派只授予这条工单的协作读取与处理权限，不授予完整项目、客户或其他工单。旧处理人转派后如没有其他可见基础，将失去读取和处理权限。主管不能利用工单协作权限管理其他部门项目。列表及历史每页50条，可继续加载。

## 状态与责任

状态流转请按本节操作顺序执行；详细状态图保留在随包源码对应说明中。

指派、方案待复核、关闭、重开和取消会产生站内通知，可从通知打开工单。通知只复制编号/状态，读取详情仍重检权限；不向外部平台发送。

所有成功写入在同一Serializable事务中保存工单、追加事件、站内通知、幂等回执与审计；事件包含操作人姓名快照、前后状态和原因，重开另保留原方案。版本过期拒绝，重试相同请求返回原回执，同请求不同输入拒绝。回执重放仍校验实时人工会话和工单可见范围。说明文本始终作为数据，不解析其中的指令。


# 私有证据附件 · 第一批

项目、项目任务和售后工单详情新增附件区。文件只通过登录后的业务接口读取，没有公开文件URL；列表与审计只返回元数据，正文不会复制进命令回执、审计或MCP工具。当前不提供智能体上传/下载工具。

## 使用与权限

1. 在有执行权限的项目、任务或工单详情中点击“上传附件”。选择PDF、PNG或JPEG，核对来源与上传权利并勾选确认。
2. 单文件上限1MiB；文件扩展名和文件头必须匹配。系统尚未进行病毒扫描，文件只下载保存，不在CRM内直接执行或内嵌预览。
3. 列表展示文件名、大小、SHA256摘要与上传时间。下载时服务端和浏览器校验完整性，下载保存为文件；接口响应禁止缓存。
4. 上传人或管理员可在对象仍允许编辑时填写原因撤回。撤回不删除原件、不释放历史容量；保留撤回原因，只有仍具所属对象读取权限的管理员可追溯下载撤回原件。

管理员、项目经理及其部门主管可维护进行中项目证据；当前任务处理人可维护本人任务证据；售后项目管理人或当前处理人可维护未解决工单证据。仅有跨部门任务/工单协作读取不授予项目级附件编辑权限。老板只读。

## 验收与历史

项目正在验收审核时，项目及任务附件冻结；任务完成、项目完成或取消后也冻结。售后工单提交解决方案、关闭或取消后附件冻结，需先依业务流程退回重办。上传/撤回必须携带用户核对过的父记录版本（`expectedParentUpdatedAt`），父记录在此之后有任何变化（如提交审核又被退回重办）即拒绝，防止延迟请求把上一轮材料加入新一轮证据；成功后同步改变父记录版本，旧页面不能在未刷新核对新增证据时直接提交完成/验收。项目详情中的任务完成事件只向能读取该任务的人显示附件元数据，其他项目协作人只看到被隐藏的数量。

任务完成、项目提交验收、工单提交解决方案的不可变事件保存当时有效文件的ID、名称、大小及SHA256。重办后撤回文件不会改写这些历史快照；原件随历史保留。

所有附件写入使用共享AttachmentService、Serializable事务、实时会话/人员/权限校验与持久化幂等回执。权限撤销后，重放旧请求也不能绕过当前读取范围；并发上传不能突破企业容量。下载仅在企业/父对象范围与内容Hash验证通过后返回，并记录不含正文的下载审计；列表与下载响应带 `Cache-Control: no-store` 与 `X-Content-Type-Options: nosniff`。

## 容量、部署与备份

本批企业历史保留容量16MiB，每个对象最多100条附件历史，列表完整返回这100条。容量包含撤回记录；界面会明确拒绝超额上传，不静默截断或丢弃旧件。扩大容量与大文件对象存储需要另外做容量、性能、恢复与保留策略验收。

新增`202611010011_evidence_attachments`迁移，只新增一张二进制证据表，不修改原验收。文件以二进制保存在MySQL中，文件名不用于服务器路径。既有AES-256-GCM加密数据库备份同时包含元数据和原文件；恢复新库后重新登录，可验证原Hash并下载原件。备份SQL整体128MiB上限仍有效。加密备份不等于运行中数据库磁盘加密；主机/数据库磁盘保护由部署环境提供。

部署顺序：备份旧版本 → 停止旧API → 执行增量迁移 → 启动同版本API与网页 → 检查ready及角色读取。不要向已有库重播演示种子。恢复遵循PRODUCTION_INSTALL手册的新库恢复方式，不自动覆盖原库或提升到生产。


# 人员、部门与会话操作

本批为 C2 人员与会话基础闭环。当前只支持管理员、销售主管、销售、老板四种预置角色，每个新建或变更账号选择一种角色，避免混合角色导致数据范围与写权限意外叠加。自定义角色定义写入暂不开放。

## 空企业首次配置

1. 用安装时设置的企业编码、管理员账号和密码登录。
2. 系统管理 → 组织部门 → 新建部门。可设置编码及上级；禁止跨企业引用、循环层级、同企业重复编码。新部门先不设置负责人。
3. 系统管理 → 新建用户。设置账号、姓名、部门、角色及唯一初始密码；密码至少12位，含大小写字母和数字，最多72个 UTF-8 字节。创建用户和分配角色在同一事务中完成，不会留下创建一半的账号。
4. 用户分配到部门后，编辑该部门设置有效成员为负责人。审批设计器仍会检查负责人实际审批权限；人员迁出、停用或失去适用角色后会清除旧负责人引用，管理员需重新指定负责人。
5. 配置并发布所需审批流。正式安装不会自动创建同名演示人员或预置审批人，不能把管理员当作默认自动审批人。

人员列表支持服务端分页、账号/姓名查询和刷新；角色列表展示四种预置权限；业务审计显示已完成的人员与组织变更。

## 调岗、变更角色及离职

系统管理 → 用户账号 → 编辑/停用：修改部门、角色、姓名或状态。保存使用版本校验；其他管理员或新登录造成版本变化时，刷新后重新编辑。更改角色、部门或状态会撤销目标用户全部会话，下一次请求必须重新登录。

不能停用自己或移除自己的管理员角色。多人同时操作也必须保留至少一名有效管理员；不会因为并发互相停用而将企业全部管理员关闭。新增和重新启用账号检查企业有效账号额度。

仍有待处理审批节点的用户暂不能调岗、换角色或停用，应先完成、撤回或转审相关审批，避免留下无人处理的审批。紧急撤销访问可先重置其密码，系统会撤销全部会话并清除登录失败锁定。C6/C11已提供单人及会签待办转审和管理员恢复。

停用和离职不删除客户、合同、订单或审计历史。先使用客户整体归属交接、项目经理/任务交接、审批转审和售后转派分别处理未完职责；销售归属交接不替代其他职责交接。部门仍有有效成员或下级部门时不能停用。

## 密码与会话

- 右上角 → 账号与安全：输入原密码、新密码及确认值，成功后全部设备会话失效，使用新密码重新登录。
- 管理员展开用户行 → 重置密码：设置新密码，撤销该用户全部设备会话，清除其登录失败锁定。不返回原密码或密码哈希。
- 右上角 → 退出登录：服务端撤销当前会话，其他已登录设备继续有效。服务器未确认时会提示重试，不把仅清除浏览器状态视为服务端退出成功。
- 账号与安全 → 退出全部设备：撤销本人全部会话；列表只显示本人有效会话，不显示访问令牌、刷新令牌或刷新哈希。
- 同一账号最多保留20个有效会话。每个会话最长7天（默认配置），刷新令牌轮换不会延长数据库中的绝对到期时间。
- 访问令牌失效时浏览器仅发起一次共享刷新请求，刷新成功后重试原请求；刷新令牌重复使用时，服务端撤销整个相关会话，要求重新登录。
- 同企业编码与用户名的失败记录按大小写不敏感归一，15分钟窗口失败8次后暂限登录；失败记录在数据库中持久化，重启不绕过。该限制不能替代正式网络入口的流量限制和监控。

密码更改、登录/退出、刷新与重放、安全会话撤销都有审计或持久化状态；密码、令牌和密码哈希不进入业务变更结果及幂等回执。


# AI工作台、平台集成与故障处理
AI规则摘要当前由确定性规则生成，未接大模型。客户查询按本人实际范围执行。独立委托、人工核对、代理执行、回执和补偿的完整步骤见同包《AI特点与智能体接入说明》。不得把一次人工批准扩大为后续任意业务授权。
钉钉/飞书由管理员在集成页进行连接测试、部门与成员预览。配置只放本机环境；没有企业凭证时会明确失败。令牌成功只证明鉴权，尚须核对通讯录权限与范围。当前不免登、不导入人员、不外发消息、不同步审批。真实企业尚未联调。

## 常见提示与处理
|提示|操作|
|---|---|
|登录或会话失效|重新登录；确认企业编码、账号状态与密码；刷新重放会撤销会话|
|无权限或未找到|检查当前企业、角色、归属和协作职责；不要修改请求中的企业编号|
|版本已变化|关闭旧详情，重新读取并核对其他人的改动，再提交|
|审批人不可用或不能自审|由管理员检查发布版本与节点人员；不可用通用表单绕过|
|职责未交接不能停用|分别交接客户、项目/任务、待审意见和未关闭工单|
|附件超限或文件头不符|检查1MiB、PDF/PNG/JPEG及历史容量；撤回不会释放历史容量|
|余额或凭据冲突|核对当前台账、更正链、有效核销和合同，不能覆盖旧账|
|请求超时|回读记录与历史确认结果，未确认前不重复建立业务|
